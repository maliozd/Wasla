# Testing

## Purpose and scope

This document says which checks exist and how to report them. It does not list every test method.

Source of the commands below: `Wasla.sln`, `tests/Wasla.UnitTests`, `tests/Wasla.PrintBridge.Tests`, `.github/workflows/ci.yml`, `scripts/ci/select-test-scope.ps1`, `scripts/ci/record-test-shard.ps1`, `scripts/ci/assert-test-shards.ps1`, `scripts/ci/assert-test-results.ps1`, and `scripts/ci/terminology-guard.js`. There is no repository `package.json` and no npm test script.

### Test scope

`scripts/ci/select-test-scope.ps1` (the `plan` job) chooses the scope after the [jobs](#job-selection), plans its [shards](#test-shards), logs both with the filters, and adds them to the job summary. The test steps are named `Run Wasla.UnitTests <shard> (fast)` or `(full)`, and `Run Wasla.PrintBridge.Tests (fast)` or `(full)`.

| Event | Scope | `Wasla.UnitTests` | `Wasla.PrintBridge.Tests` |
| --- | --- | --- | --- |
| Pull request into `dev` whose changes allow it (see [Job selection](#job-selection)) | fast | `--filter "Category!=Browser"` | `--filter "Category!=WebView2Runtime"` |
| Pull request into `dev` whose changes need the full scope (CI, build or planner files, code the deferred tests run, the deferred tests themselves, an untrusted diff; see [Job selection](#job-selection)) | full | No filter: every test | No filter: every test |
| Push to `dev`, pull request into `master` (also when its base changes to `master`), push to `master`, manual run on any branch | full | No filter: every test | No filter: every test |

Any other event or base branch also gets the full scope. Both scopes run the terminology guard, build the whole solution in every Windows job, run every tracked Node test, check the prerequisites, require every selected test to run exactly once and pass, report leftover processes and upload the results.

The fast scope defers two groups, each named by a trait:

- `Category=Browser` (`Wasla.UnitTests`): the test classes that start a real headless browser through `HeadlessChromium` (35 classes, 200 test methods). The trait is on the class, so a class's few tests that do not open a browser are deferred with it.
- `Category=WebView2Runtime` (`Wasla.PrintBridge.Tests`): the tests that host the real WebView2 Runtime (22 test methods).

A test without one of these traits runs in both scopes, so a new test is in the fast scope until its author tags it. Give a new class that starts a real browser `[Trait("Category", "Browser")]`, and a new test that needs the real WebView2 Runtime `[Trait("Category", "WebView2Runtime")]`. Do not use either trait to move a test that needs neither out of pull requests; that is a change to this policy. To check that the two selections still cover the discovered suite, list both against the build output and compare them with the whole list (PowerShell, after a Release build):

```powershell
$exe = 'tests/Wasla.UnitTests/bin/Release/net8.0/Wasla.UnitTests.exe'
$all = & $exe -list tests | Where-Object { $_ -like 'Wasla.*' }
$fast = & $exe -list tests -trait- 'Category=Browser' | Where-Object { $_ -like 'Wasla.*' }
$deferred = & $exe -list tests -trait 'Category=Browser' | Where-Object { $_ -like 'Wasla.*' }
"$($all.Count) = $($fast.Count) + $($deferred.Count)"
Compare-Object $all ($fast + $deferred)
```

`Compare-Object` prints nothing when every test is in exactly one selection. For Print Bridge use `tests/Wasla.PrintBridge.Tests/bin/Release/net8.0-windows/Wasla.PrintBridge.Tests.exe` and `Category=WebView2Runtime`.

Other in-process integration tests stay in the fast scope, among them the web-host tests for authentication, tenant isolation, session revalidation and rate limits, the realtime hub and load tests and the SQL Server concurrency tests. Since the browsers left the fast scope they are most of its remaining time.

### Job selection

`select-test-scope.ps1` chooses which jobs run (WAS-246), from the files a change touches and the rules in `scripts/ci/ci-job-rules.json`, and then the [scope](#test-scope) of a pull request into `dev`. The two are separate decisions, each with its own reasons in the summary.

The jobs: whether the two Windows jobs run.

- `unit-tests`: every shard of the scope, or none;
- `print-bridge`: the installers and `Wasla.PrintBridge.Tests`.

`terminology-guard`, `javascript-tests` and `integrations-consumer` run for every change; `plan` and `test-accounting` always run.

The scope, chosen after the jobs: a pull request into `dev` runs the fast scope unless its changes need the full one (below); every other event runs the full scope. The full scope adds the three browser shards to `unit-tests` and the WebView2 runtime tests to `print-bridge`, in whichever of the two jobs runs.

| Event | Jobs |
| --- | --- |
| Pull request into `dev` | The jobs its changed files need (below). Changes: from the merge-base of the pull request's base and head to its head, as **Files changed** shows them |
| Push to `dev` | Every job (observation phase, below). The plan also records what the rules would have selected for the push's changes, from its previous commit to its new one, every pushed commit included |
| Pull request into `master`, push to `master`, manual run, any other event | Every job |

The `plan` job checks out the whole history and diffs with `git diff --name-status -M`. Every changed file is matched against the rules in order; the first rule whose path matches decides, and the pull request runs the union of the jobs its files need. Every job runs when:

- a matching rule needs every job;
- a file matches no rule (the rules are an allowlist: a new folder runs everything until a rule covers it);
- a file is deleted, renamed, copied or changes type;
- the diff is empty;
- the changes cannot be computed: a commit missing from the fetched history (a force push, a shallow clone), a push without a previous commit (a new branch), a missing event payload, a git error.

Then the scope. A pull request into `dev` runs the full scope when:

- a changed file's rule needs it (the **Scope** column below). A rule needs the full scope when:
  - the tests the fast scope leaves out run its files. The headless-browser tests start `Wasla.Web`, and the WebView2 runtime tests start the `Wasla.PrintBridge` tray app, each with the projects it builds on (Web: Contracts, Application, Infrastructure, Domain; the tray app: `Wasla.PrintBridge.Core`, Application, Domain);
  - its files are those tests themselves, or the headless-browser driver;
  - it changes how the tests are built, selected or counted (`ci-and-build`, this planner included);
  - its dependencies were not analyzed (`deployment`, `report-export-smoke`);
- every job runs for a reason other than a rule, from the list above: the diff is not trusted.

Otherwise it runs the fast scope, also when every job runs because of a rule with the fast scope (`print-bridge-service`). This automates most of the [full validation](#full-validation-of-a-feature-branch) the pull requests that change those areas used to need by hand.

`scripts/ci/ci-job-plan.test.js`, part of the Node suite, has three groups of tests:

- **Decisions:** table-driven tests of every rule, each with the jobs and the scope it expects; mixed changes; every combination of focused or every job with the fast or full scope; unknown paths, deletions, renames, copies, type changes, empty diffs, missing history and git errors; the diff of a pull request from its merge-base and of a multi-commit push, in temporary git repositories; and every event.
- **Final job:** its checks of the job results, and the scope it reports.
- **Guards** against this repository:
  - every project a test project compiles must be in a rule that runs that project's job;
  - every file a project links from another folder must be in a rule that runs every job;
  - every `src`, `tests`, `installer`, `deploy` or `scripts` folder its tests name in a string literal must be in such a rule. A folder named without a subfolder counts every folder under it;
  - every Markdown document its tests read must be in such a rule;
  - every test class with `Category=Browser` or `Category=WebView2Runtime`, and the file that defines `HeadlessChromium`, must be in a rule that runs its job in the full scope;
  - `Wasla.Web`, `Wasla.PrintBridge` and every project they build on must be in a rule with the full scope.

The guards run with the Node tests on every change, so a new dependency fails CI until the rules cover it. They find literal paths, project references and trait attributes only: a path a test builds at run time is not found, so review new file reads in tests with that in mind.

To change a rule, edit `ci-job-rules.json` (the first matching rule wins: put a narrower path before a broader one) and add a case to `ci-job-plan.test.js`. A rule without a valid `scope` gets the full scope. A change to the rules or the planner runs every job and the full scope.

#### Running every job by hand

On any branch, **Actions → CI → Run workflow** or `gh workflow run ci.yml --ref <branch>` runs the full scope and every job (see [Full validation of a feature branch](#full-validation-of-a-feature-branch)). No label or input narrows the selection: the plan reads only the event's name, its base branch and its commits.

#### Reading the summary

- **The `plan` job's summary:**
  - **Test scope: fast** or **full**, with the reason: for a pull request into `dev`, the first finding that needs the full scope and how many more there are, or that no changed file needs it;
  - **Jobs: focused** or **Jobs: every job**, then the scope again, with the changes it compared (merge-base and head, or the previous and new commit) and how many files changed;
  - a table of the jobs, each with whether it runs and why;
  - a table of the rules the changed files matched, with the jobs and the scope they need and the files (the first 20 per rule);
  - when every job runs, the findings that caused it; when the full scope runs, the findings that caused it (the two lists overlap for an untrusted diff);
  - the shards of the scope, with their filters.
- **Skipped jobs in the pull request's checks:** a job the plan left out shows as skipped; the unit-test matrix shows as one skipped check. It is skipped on purpose only when the final job, **Require every planned job and test to run and pass**, passes. In the full scope the unit-test checks include `browser-1`, `browser-2` and `browser-3`, and the Print Bridge test step is named `(full)`.
- **The final job's summary:**
  - **Planned scope**, with its reason;
  - every job, planned or "skipped on purpose", with its result and why;
  - then the test accounting of the planned .NET projects in that scope: every test of the scope, the browser shards included in the full scope, ran exactly once.

  It fails when a planned job failed, was cancelled or was skipped, when a job the plan left out ran, and when a shard of the planned scope is missing or ran another scope.

#### Observation phase on `dev`

Every push to `dev` still runs every job and the full scope. The `plan` summary also shows what the rules would have selected for a pull request with the push's changes: the jobs and the scope. The final job lists each job the rules would have skipped, with its real result. A failure there adds a warning, **Job selection would have missed a failure**. When the rules would have chosen the fast scope, the test accounting also lists every failed test that scope leaves out (`Category=Browser`, `Category=WebView2Runtime`) in a job the rules would have run, with the warning **The fast scope would have missed a failure**. In both cases check whether the change caused it (then a rule, or its scope, is wrong) or it is unrelated (for example WAS-229 or WAS-244). Until it is decided otherwise (WAS-246), every push to `dev` keeps running every job and the full scope.

### Test shards

The Windows work of a scope is split into jobs that run in parallel on separate runners (WAS-243). `select-test-scope.ps1` defines each shard as rules on traits and on prefixes of the fully qualified test name (`Namespace.Class.Method`), turns them into its `dotnet test --filter`, and gives it a limit on the test classes xUnit runs at once (none: xUnit's default, one per CPU, four on `windows-latest`). A namespace prefix ends with a dot, so it covers the namespace and every namespace below it, and `Wasla.UnitTests.Auth.` does not cover `Wasla.UnitTests.Authorization`.

| Project | Shard | Tests | Classes at once | Scopes |
| --- | --- | --- | --- | --- |
| `Wasla.UnitTests` | `nonbrowser-1` | Not `Category=Browser`, namespaces `Auth`, `Routing`, `Printing`, `Contact` | default | fast and full |
| `Wasla.UnitTests` | `nonbrowser-2` | Not `Category=Browser`, every other namespace | default | fast and full |
| `Wasla.UnitTests` | `browser-1` | `Category=Browser`, classes of the `Web` namespace whose names start with `L`, `O` or `P` | 2 | full |
| `Wasla.UnitTests` | `browser-2` | `Category=Browser`, the other classes of the `Web` namespace | 2 | full |
| `Wasla.UnitTests` | `browser-3` | `Category=Browser`, every other namespace | 2 | full |
| `Wasla.PrintBridge.Tests` | `print-bridge` | The scope's Print Bridge tests, in the job that also builds the installers | default | fast and full |

A new test needs no shard of its own: its traits, namespace and class name place it. The prefixes were chosen from the class durations of the 2026-11-23 runs so the shards of a group take about as long: about 37 and 40 minutes of test-class time for the two non-browser shards, and about 38, 39 and 35 for the three browser shards. `SignupFlowBrowserTests` (9 to 17 minutes) is the longest single class, so `browser-3` cannot finish sooner. When a shard grows much longer than the others of its group, move a prefix between them in `select-test-scope.ps1`; the accounting below proves the new rules still cover every test once.

The browser shards run at most two test classes at once. In the single Windows job before WAS-243, browser classes shared the runner with the other tests, and four browser tests ran at once at most 11 % of the time (one or two most of the time). The first shard layout ran four browser classes at once for 43 % of its time; three realtime browser classes then started together and `RealtimeLifecycleBrowserTests` missed its 8-second wait for a pushed order (run [45258289534](https://github.com/maliozd/Wasla/actions/runs/45258289534)). The limit keeps every browser test at a density no higher than that job usually had; it does not change any test or wait.

Each shard job records, before its tests run, the commit it checked out, its scope, filter and limit, and the test methods its assembly lists (`record-test-shard.ps1`, which runs the xUnit v3 test executable with `-list full/json`). The `test-accounting` job reads those records and the TRX files and runs `assert-test-shards.ps1` for the projects whose job the plan selected (none when the [job selection](#job-selection) runs no .NET job). It fails when:

- a planned shard has no record or no TRX file, a TRX file has no results, or a record belongs to a shard the plan does not have (a shard of a project whose job the plan left out included);
- a shard tested another commit, scope, filter or limit on classes at once than planned;
- two shards of a project listed different test methods;
- the shard rules do not partition the scope: a test of the scope that no shard or two shards select, a shard that selects a test outside the scope, or a shard with no test of the scope;
- a shard did not run one of its planned methods, ran a method it was not planned for, or a method ran in two shards.

Methods are compared by class and method name; a theory's data rows count as one method. The same job then runs `assert-test-results.ps1` over every shard's TRX file, so a failed or skipped test fails it too. The shard jobs check their own results as well, so a failure shows on the job that had it. `scripts/ci/test-shards.test.js` (part of the Node suite) checks the scope and shards of each event and each accounting failure above with made-up results.

To run one shard locally, take its filter and limit from the plan, for example `.\scripts\ci\select-test-scope.ps1 -EventName push`, and pass them to `dotnet test --filter "<filter>" -- xUnit.MaxParallelThreads=<limit>` (leave out the part after `--` for a shard without a limit).

### Full validation of a feature branch

A green fast run does not cover the browser or WebView2 runtime tests. A pull request into `dev` that changes `Wasla.Web`, Domain, Application, Infrastructure, Contracts, the Print Bridge tray app or engine, this workflow or its scripts, or whose diff is not trusted, already runs the full scope (see [Job selection](#job-selection)): that covers authentication, authorization and tenant isolation, payment, signup and provisioning services, data integrity and migrations, the Web layouts, Live Screen and other browser-visible behavior, and the Print Bridge WebView2 app and tray. Run the full scope by hand on the branch before merging a pull request into `dev` whose own run kept the fast scope but that needs the full one anyway, for example a CLI change to provisioning, or one that comes from a machine where the full suite is not run locally:

```bash
gh workflow run ci.yml --ref <branch>
```

Or open **Actions → CI → Run workflow** and choose the branch. The run tests the branch's head commit at that moment and runs every job, whatever the branch changes; it shows in the pull request's checks with `(workflow_dispatch)` after the job name. Make sure its commit is the pull request's head, and run it again after a later push that should be covered.

### Tradeoff: `dev` can fail after a merge

A pull request into `dev` can merge with only the jobs its changes need, and with only the fast scope green when its changes allow it (documentation, tests without the deferred ones, Api, CLI, Worker, the Print Bridge service and installer). The full scope and every job then run on the push to `dev`, so `dev` can turn red for a failure in a job the pull request did not run, or in a browser or WebView2 runtime test it did not run (for example through a test helper the deferred tests share with others). Treat a red `dev` run as the first thing to fix (fix forward or revert), and do not open a pull request from `dev` into `master` until the latest `dev` run is green. `master` gets no unvalidated change: pull requests into `master` and pushes to `master` always run the full scope.

Moving a pull request's base to `master` starts the full scope by itself: `.github/workflows/ci-base-change.yml` reacts to an edit of a pull request into `master`, and when the edit changed the base it runs the CI workflow on the merge with `master`. The event still carries the merge with the old base, so its first job (`Find the merge with the new base`) waits, up to 10 minutes, until GitHub's merge commit has the current `master` and the pull request's head as parents, and the CI workflow checks out that commit. It fails, rather than skips, when it cannot read the pull request, when the pull request conflicts with `master` or when no merge commit appears. The CI checks are named `Full CI after base change / ` followed by the CI job names. They replace an older run of that pull request that is still in progress. A title or description edit only skips its jobs and starts no CI run. Moving a base from `master` back to `dev` starts nothing; the existing full checks stay. Re-running an old run keeps the event and base branch it started with, and so its scope.

Prerequisites on the Windows runner:

- The headless browser is the runner image's Microsoft Edge. Every `unit-tests` job sets `WASLA_TEST_BROWSER` to it and fails before the build if Edge is missing.
- The WebView2 runtime tests use the image's WebView2 Runtime and the runner's interactive desktop session. Windows stay off-screen.
- The Print Bridge runtime tests need at least one installed printer on the runner. Nothing is sent to it.
- The Print Bridge installer tests (`PrintBridgeInstallerTests`, WAS-62) first check, from the files themselves, that the two setups the `print-bridge` job's `Build Print Bridge installers` step built from the same commit are different builds: SHA-256, the setup EXE's and the MSI's version, the version of the two executables in the MSI, different product codes and one upgrade code. Both are signed with a throwaway self-signed certificate the step creates and only that runner trusts (WAS-63; `-TestSigning`, "test-signed development build"), and the check confirms that each file's Authenticode signature matches its metadata. That check changes nothing and also runs locally when `WASLA_PRINT_BRIDGE_SETUP` and `WASLA_PRINT_BRIDGE_UPGRADE_SETUP` name two local builds (signed or unsigned). The update test (WAS-63) installs the older setup without the sign-in start, lets the installed service find, download, verify and stage the newer one from a fake server (a tampered download is refused), runs the staged setup with `FailWhenDeferred=1` so Windows Installer rolls back, then runs it again to a committed update, and checks data, the user's Stop, the startup choice, the service's whole configuration as `sc.exe` reports it (privileges and recovery included, against the installed version's) and the health check each time; the failure is induced and no machine reboot happens. The other two install the older setup, repair it, upgrade it to a build with the next build number, refuse the older setup and MSI, and uninstall it; they also start the installed app as its sign-in entry does and show its WebView2 runtime notice while the service prints (an empty runtime folder set for `Wasla.PrintBridge.exe` only through WebView2's `BrowserExecutableFolder` machine policy: the elevated app ignores `WEBVIEW2_*` environment variables). They run only on GitHub-hosted runners (elevated, disposable) and skip elsewhere; only the installers' version and SHA-256 metadata is uploaded (`print-bridge-installer-metadata`), and the setup and MSI logs, with the installed app's and the service's logs, are in `dotnet-test-results-print-bridge`. See [print-bridge-installer.md](../integrations/print-bridge-installer.md#verification).
- The Print Bridge Windows Service test (`PrintBridgeWindowsServiceTests`, WAS-61) and the cross-account tests need the runner's elevation and run only on GitHub-hosted runners: they register a uniquely named instance of the built service with `sc.exe`, protect its data folder with `secure-data`, create temporary local accounts and a disposable machine printer ("Generic / Text Only" on a loopback TCP/IP port), and remove all of it afterwards. Elsewhere they skip. `WindowsPrintSpoolerTests` (WAS-216) also need the runner: they install a disposable "Generic / Text Only" printer whose loopback TCP/IP port the test listens on (or does not), and check the winspool boundary against the real spooler: job ids, written bytes and finishing, a job that leaves the queue and reaches the port once, a paused queue, jobs that stay queued while nothing listens and are sent once it does, finding a job by its document name, reading another document's job id as not ours, and a removed printer. That is spooler and port evidence, not paper. The engine's own decisions about each Windows outcome run everywhere against a scripted queue (`PrintOutcomeTrackingTests`, `PrintSubmissionTrackerTests`). `WindowsPrintSpoolerNativeResultTests` run `WindowsPrintSpooler` itself, everywhere, against scripted winspool results (return values, last errors, reported byte counts and job listings): failed, partial, zero-progress and implausible writes, and failed, growing and truncated job listings, which the real spooler does not produce on demand. `PrintBridgeServiceProcessTests` start the built `Wasla.PrintBridge.Service.exe` as separate processes (no elevation) and run everywhere. See [print-bridge-service.md](../integrations/print-bridge-service.md#developer-validation).
- The headless-browser tests need `cdn.jsdelivr.net`, except `MarketingVendorFilesBrowserTests`, which resolves every host but the test host to nothing on purpose. Tests make no other network calls in CI, the workflow uses no repository secrets, and every test server is in-process with fake tokens and data.
- The runner has no developer environment: no `ENCRYPTION_MASTER_KEY`, user secrets, certificates or local databases. The runner image does ship the SQL Server LocalDB runtime (with Visual Studio); the [SQL Server concurrency tests](#sql-server-concurrency-tests) create their own throwaway database on `(localdb)\MSSQLLocalDB`. A test host that registers the real Infrastructure services must replace `ISecretManager` with a fake (as `TenantVisualWebHost` and `TenantSessionApiHost` do); otherwise a test can pass on a developer machine and fail in CI. `TenantVisualWebHostTests` checks the visual host without the variable.
- The runner reports `prefers-reduced-motion: reduce`, and a developer machine usually does not. The headless-browser driver (`HeadlessChromium`) therefore starts every browser emulating `prefers-reduced-motion: no-preference`, so a page renders the same everywhere. A test that needs reduced motion sets it for its own browser with `SetReducedMotionAsync("reduce")`. AdminLTE 4.0.0-rc3 displays every `.fade` element under reduced motion, which let a closed modal cover the page (WAS-100); `wasla-theme.css` keeps closed modals hidden, and the `UnderReducedMotion_*` tests in `TenantDarkModeBrowserTests` and `AdminMobileNavigationBrowserTests` check a tenant and an Admin modal at desktop LTR and phone RTL.

The `unit-tests` jobs log the browser version, and the `print-bridge` job the WebView2 Runtime version and the number of installed printers, before the build. Print Bridge tests use SQLite only, so only the `unit-tests` jobs start LocalDB.

How failures surface:

- A build error or a failing test fails its step and the job. The other test jobs still run, so one run reports every shard and both projects.
- `scripts/ci/assert-test-results.ps1` then reads the job's result file, and the `test-accounting` job reads every shard's, in both scopes. It fails the job when a file is missing, has no tests, or reports a failed or **skipped** test. A filter that selects no test still writes a result file and `dotnet test` still exits with 0, so this check is what fails such a run. A missing browser, an unreachable CDN, a missing WebView2 Runtime or a missing printer therefore fails CI instead of passing as a skip. The script adds an error annotation per failed or skipped test (first 20) and a totals table to the job summary.
- A test that hangs for 15 minutes is stopped by `--blame-hang-timeout`. The run then fails with the hanging test's name and no memory dump. Each job also has a time limit (60 minutes for each Windows job, see the measurements above; 15 for Node; 10 for the accounting).
- `test-accounting` fails when a planned job did not pass or a job the plan left out ran (see [Job selection](#job-selection)), and when a test of the scope did not run, ran twice or in the wrong shard, or a shard is missing or empty (see [Test shards](#test-shards)).
- After the tests, each Windows job warns (it does not fail or kill anything) when an Edge, WebView2 or test host process outlived them.
- Results are kept for 14 days as the `dotnet-test-results-<shard>` (TRX files, the shard's record and its assembly's test list; `dotnet-test-results-print-bridge` also has the installer logs) and `javascript-test-results` (JUnit XML) artifacts. They contain test names, messages and output from fake data only.

To find a failure: open the failed run. The annotations name each failed or skipped test with the first line of its message, on its shard's job and again on `test-accounting`, and the job summaries have the totals per shard. Download the artifact for the full messages and stack traces (the TRX files open in Visual Studio or any XML viewer). A headless-browser page that does not finish loading reports where the page is and what it still waits for. `chrome-error://chromewebdata/` means the server answered with an error. Tests served by `TenantVisualWebHost` put the server's exception first.

CI does not cover browser smoke of real screens, SQL Server beyond the [SQL Server concurrency tests](#sql-server-concurrency-tests), real platform providers, real printers or physical output, a signed Print Bridge installer, Print Bridge on Windows 10 or on a computer without the WebView2 Runtime, or Print Bridge update delivery. Those stay manual.

## Retired-terminology guard

`scripts/ci/terminology-guard.js` enforces the [clean-break policy](../product/terminology.md#clean-break-policy) on the whole repository (WAS-144). The CI job `Retired-terminology guard` runs it in every scope, next to the other jobs; it takes seconds.

What it checks:

- Every file `git ls-files` lists: source, tests, documentation, scripts, configuration, CI files and binary files. A staged new file is included; an untracked file is not. It reads the working tree, so local edits count.
- The content line by line and the path separately. UTF-8 and UTF-16 text with a byte-order mark is read as text. A file with NUL bytes is read as binary, in single-byte and both UTF-16 alignments, so an encoding hides nothing.
- Every match of every pattern is a finding of its own. Nothing is excluded by line or by file name: a genuine order-customer name on the same line, or in the file's name, does not hide a match next to it. Order-customer names pass because no pattern matches them.
- The only exemption is the [historical migration exception](../product/terminology.md#historical-migration-exception). `HISTORICAL_MIGRATIONS` in the script lists those exact files; their content is not scanned, their paths are. The guard fails when a listed path is no longer tracked, is listed twice, is not an exact migration designer path (a directory, a pattern or another kind of file), is not approved by the repository variable, or no longer contains a retired name. Every other file in the migrations folders, both model snapshots included, is scanned like any other file, so a new migration with a retired name fails.
- It does not look for order-customer prose or for a tenant value held under an order-customer name; those stay a review task (WAS-134).

The retired-term patterns are not in the repository. They live in the GitHub Actions repository variable `WASLA_RETIRED_TERMS` (Settings → Secrets and variables → Actions → Variables; a variable, not a secret, so its value can appear in logs), which the job passes to the script as an environment variable of the same name. Its value is JSON:

```json
{
  "version": 1,
  "rules": [{ "id": "<kebab-case name>", "pattern": "<JavaScript regular expression>", "flags": "i" }],
  "approvedHistoricalMigrations": ["<exact path of an approved historical migration file>"]
}
```

- `rules`: at least one. `flags` is optional and may hold `i` and `u`. A pattern that is invalid or matches an empty string is refused.
- `approvedHistoricalMigrations`: the files WAS-134 approves as exceptions. The script's list may be shorter, never longer, so the list in the repository can only shrink and a new exception needs a WAS-134 decision and a change to this variable.
- The current value and every change to it are recorded in WAS-144. Never copy the patterns into a tracked file, test fixture included; the guard's tests (`scripts/ci/terminology-guard.test.js`, part of the Node suite) use made-up terms.

A missing, empty or invalid value fails the job before anything is scanned (exit code 2), with a message that says what to fix. Findings fail it with exit code 1: each is printed as `path:line:column: [rule] "match"` (or `(file path)`, `(binary content)`, `(historical exception list)` with the problem and the change to make) and added as an error annotation on the file.

To run it locally from the repository root, with `gh` signed in to an account that can read the repository's variables:

```powershell
$env:WASLA_RETIRED_TERMS = (gh variable get WASLA_RETIRED_TERMS) -join "`n"
node scripts/ci/terminology-guard.js
Remove-Item Env:WASLA_RETIRED_TERMS
```

In a POSIX shell: `WASLA_RETIRED_TERMS="$(gh variable get WASLA_RETIRED_TERMS)" node scripts/ci/terminology-guard.js`.

To change the variable (repository admins), run the guard locally with the new value against the current branch first, then `gh variable set WASLA_RETIRED_TERMS < new-value.json` and record the change in WAS-144. The new value applies to every branch from its next run.

Print Bridge tests reference the shipped `Wasla.PrintBridge.Core` and `Wasla.PrintBridge` assemblies, and they print only to a recording fake. They never read or write `C:\ProgramData\Wasla\PrintBridge`:

- Outside those folders, the default location for the whole run is an empty canary folder (`EscapedWriteCanary`, set with `PrintBridgePaths.UseDefaultRootForTests`) instead of ProgramData or a development root. A write that escapes its folder lands there and fails the test class and the run.

| Signup JS | The signup Node tests (`tests/Wasla.UnitTests/Signup/signup-*.test.js`: steps, draft and API client, receipt and review, phone code, countdown, address check, address search, phone format, viewport, business types, plan price), `SignupPageMarkupTests`, and `SignupFlowBrowserTests` for page behaviour |
| Registration status and checkout pages | `RegistrationStatusPagesRenderedTests` (with `RegistrationStatusPresentationTests`), `CheckoutReviewPriceRenderedTests`, `PublicPlanPricesRenderedTests`, `SignupRenderedResponseTests`, `SignupAbuseProtectionTests` and `SharedResourceParityTests`; these render the real pages in-process with no browser or SQL Server. A manual smoke in the isolated Development environment for visual changes |
| Migrations | Confirm `--context` and `--output-dir` before generating anything. Build the affected projects. Do not apply migrations to a shared database from a doc or unrelated task. See [migrations.md](migrations.md) |
| Docs only | Link check of the edited Markdown and `git diff --check`. No product build is required |
| Terminology guard or `WASLA_RETIRED_TERMS` | `node --test scripts/ci/terminology-guard.test.js`, then the guard on the branch with the variable's (new) value; see [Retired-terminology guard](#retired-terminology-guard) |

Browser smoke means opening the affected tenant screen and exercising the changed control. Razor compilation is not that check.

Local runs follow the risk of the change. Run the affected tests and the tests of the contracts the change depends on or exposes; a full local suite after every task is not required, and GitHub Actions supplies the Windows, browser and WebView2 runs. Do not run a full suite locally again for a commit that already has a green full CI run, or the reverse. Changes to security, authentication or tenant isolation, payment or provisioning, data integrity or migrations need full verification before they are merged into `dev`: a full local run where that machine is meant to run one, otherwise the [manual full run](#full-validation-of-a-feature-branch) of the branch. Avoid starting several full suites at once from different worktrees on one machine.

## Realtime load tests

`tests/Wasla.UnitTests/Realtime/RealtimeLoadTests.cs` (WAS-25) runs the live hub under bounded load: the real Web pipeline in-process and many lightweight .NET SignalR clients over WebSockets, one per "tab" of a signed-in user. It runs with the rest of `Wasla.UnitTests` in every CI run at its default size, in its own collection (`RealtimeLoadCollection`) that runs alone: its server, clients and the notifier's send timeout share the process's thread pool, so another test class running at the same time would add its waits to the measured send times. Every wait has a timeout, every count an upper bound, and the tests stop only what they started (their own in-process host and clients; no browser).

| Variable | Default | Allowed | Meaning |
|----------|---------|---------|---------|
| `WASLA_REALTIME_LOAD_CONNECTIONS` | 120 | 12–2000 | Hub connections across all tenants and roles |
| `WASLA_REALTIME_LOAD_EVENTS` | 200 | 10–5000 | Notifications per tenant in each burst |
| `WASLA_REALTIME_LOAD_TENANTS` | 3 | 2–10 | Tenants |

A value outside its range fails the test instead of being clamped. The revocation test uses at most 80 connections and 3 tenants whatever is set. The heavier run, for a developer machine before a release or after a change to the hub (PowerShell, from the repository root):

```powershell
$env:ENCRYPTION_MASTER_KEY = $null
$env:WASLA_REALTIME_LOAD_CONNECTIONS = "1000"; $env:WASLA_REALTIME_LOAD_EVENTS = "1000"; $env:WASLA_REALTIME_LOAD_TENANTS = "5"
dotnet test tests/Wasla.UnitTests/Wasla.UnitTests.csproj --configuration Release --filter "FullyQualifiedName~Wasla.UnitTests.Realtime.RealtimeLoadTests" --logger "console;verbosity=detailed"
Remove-Item Env:WASLA_REALTIME_LOAD_CONNECTIONS, Env:WASLA_REALTIME_LOAD_EVENTS, Env:WASLA_REALTIME_LOAD_TENANTS
```

Each test writes its sizes, durations, send-time percentiles and the test process's threads, handles and memory to the test output. The figures describe the machine that ran them, with server and clients in one process; they are not a production capacity claim. `RealtimeLifecycleBrowserTests` is the real-browser layer: one browser at a time with a fixed number of Live Screen pages.

## SQL Server concurrency tests

`OrderActionConcurrencySqlServerTests` (WAS-104), `OrderSyncStatusRaceSqlServerTests` (WAS-123), `OrderIngestionInsertRaceSqlServerTests` (WAS-18), `ManualOrderPrintRaceSqlServerTests` (WAS-119), `TrendyolGoMealWebhookPollingRaceSqlServerTests` (the Meal webhook stage pilot's reconciliation racing a polling pass), `TenantSessionRegistrySqlServerTests` with `TenantSessionMigrationSqlServerTests` (WAS-114), `PrintBridgeTransferSqlServerTests` (WAS-91) and `PrintBridgeDeviceConcurrencySqlServerTests` (WAS-190) (both on a throwaway CentralDb from `SqlServerCentralDatabase`), `RegistrationDraftSqlServerTests` with `RegistrationDraftMigrationSqlServerTests` (WAS-192, a throwaway CentralDb `Wasla_SignupTest_<random>` from `SqlServerSignupDatabase`), `Contact/ContactNotificationSqlServerTests` (WAS-217: the same pilot form posted at once, notification resends at once, a hanging send past the stuck window, a late outcome against a newer claim, on a throwaway CentralDb from `SqlServerCentralDatabase`), and `Contact/PilotApplicationRetentionSqlServerTests` (WAS-222: two retention runs at once delete and record each pilot application once, a run's uncommitted delete makes a second run, a recorded contact and a deletion on request wait and then find it gone, a contact recorded between the run's read and its delete keeps the application, repeated overlapping runs never deadlock (the covering retention index; the cached plan is checked for a key lookup), on a throwaway CentralDb from `SqlServerCentralDatabase`) need a real SQL Server, because SQLite does not run application locks and does not prove SQL Server locking. `CliCreateUserSqlServerTests` (WAS-42) needs one because SQLite compares emails case-sensitively and the CLI opens the tenant database with SQL Server. `OrderReportSqlServerTests` (WAS-182) needs one because SQLite cannot sum decimals and does not prove the translation of the report's local-day grouping. Each test class creates a throwaway database named `Wasla_ConcurrencyTest_<random>`, applies this build's tenant migrations, and drops only that database afterwards; no existing database is read or changed. Before dropping its database, a fixture clears only the connection pools of that database (`tests/Wasla.UnitTests/Setup/OwnedSqlServerPools.cs`), never every pool in the process: `SqlConnection.ClearAllPools` discards sessions that test classes running in parallel still expect from their own pools (WAS-229).

The server is the `WASLA_TEST_SQLSERVER` environment variable (an instance name such as `(localdb)\WaslaTests`, not a connection string), otherwise `(localdb)\MSSQLLocalDB`, which CI uses. They run with the rest of `Wasla.UnitTests`. Without a reachable SQL Server they fail rather than skip. Before the tests, CI's "Start and verify SQL Server LocalDB" step starts `MSSQLLocalDB` with `sqllocaldb start` and runs one query against it, so no test fixture pays LocalDB's first-connection start, which on a busy runner outlasted a fixture's 60-second connect timeout (#69); if LocalDB cannot start, that step fails instead of the tests. Creating and migrating each throwaway database has a 3-minute command timeout in every fixture (`SqlServerTenantDatabase.SetupCommandTimeout`), because `CREATE DATABASE` on a busy runner has outlasted the 30-second default (WAS-18, and run 42705726306 for the CentralDb fixtures). To keep them off a developer's own LocalDB instance, create a separate one first:

```powershell
sqllocaldb create WaslaTests
sqllocaldb start WaslaTests
$env:WASLA_TEST_SQLSERVER = "(localdb)\WaslaTests"
dotnet test tests/Wasla.UnitTests/Wasla.UnitTests.csproj --filter "FullyQualifiedName~SqlServerTests"
```

Every caller uses its own service, DbContext and connection pool (`Application Name` differs), as separate Web and Worker processes would. A held provider call makes the contested windows deterministic; the free races start all callers at one barrier. The Print Bridge races (`PrintBridgeSqlServerRace`) release that barrier only after every caller has opened its connection and reached it, bound each wait, and fail at once if a caller cannot connect. They assert one winner, one provider call, one `ChangeVersion` raise and one notification per contested transition, and `Orders.InvalidStatusForAction` for every loser.

`OrderSyncStatusRaceSqlServerTests` pause a Worker sync pass after it read an existing order and before its update transaction (a transaction interceptor on that sync's context), and commit another writer in that window: an operator reject while the provider reports the order accepted, an operator approve while the sync's merge keeps `New` (with a scalar change, and with an items-only change), and a second Worker applying the same payload, with and without changed items and options. They assert that sync keeps the committed status and timestamps, never moves `UpdatedAt` backwards, raises `ChangeVersion` only for a real change, does not rewrite items another Worker already wrote, and requests no receipt for a cancelled or already handled order. While sync holds its row lock, an update from another connection with a short `LOCK_TIMEOUT` must time out.

`OrderIngestionInsertRaceSqlServerTests` run two Worker passes that both read that a package has no order and both insert it: one held between its read and its insert while the other stores the order, and free races released together at one barrier (a command interceptor on each pass's order `INSERT`). They assert one order, no failed connection, no failure counter or `IntegrationError`, auto-approve and the new order's notification once, one receipt for a provider-accepted order, a loser carrying a newer status applied once through the locked update, and nothing written by a repeated delivery afterwards. A truncation error on insert still fails the connection and keeps the checkpoint, and a later pass stores the order. The duplicate-key classifier is checked against real SQL Server errors: only the order identity indexes count.

`ManualOrderPrintRaceSqlServerTests` hold a manual first print after its own read of the order's receipts, at the template read each receipt creation makes before its transaction (a service the test supplies), while a second request on its own pool queues a receipt and takes it to the state under test. A receipt that became Printed or Failed creates no copy and returns `ReprintConfirmationRequired`, an active one returns `AlreadyQueued`, and a cancelled one still prints. A confirmed print keeps creating its copy, and automatic printing still stops only for an active receipt. A command interceptor holds a first print right before its `INSERT` until `sys.dm_exec_requests` reports another receipt writer blocked by its transaction.

`TenantSessionMigrationSqlServerTests` checks the `AddTenantSessions` schema on SQL Server (columns and types, primary key, the cascading foreign key to `AppUsers`, the user index), then reverts to the previous migration and applies it again. `TenantSessionRegistrySqlServerTests` runs the real `TenantSessionRegistry` and `TenantSessionValidator` from separate pools: create, validate and revoke, revocation scoped to one session and one user and never repeated or reactivated, the cascade on user deletion, eight simultaneous sign-ins and eight simultaneous logouts of one session released at one barrier (exactly one revokes, with its own time), and a logout held behind another connection's uncommitted revocation until `sys.dm_exec_requests` reports it blocked, which then changes nothing.

`RegistrationDraftSqlServerTests` run the real draft and verification services, with the fake SMS sender, one in-memory Data Protection key ring and a test clock, from a context and pool per caller. Free races release every caller at one barrier: twelve wrong codes must use exactly five attempts and lock the number, eight checks of the right code must consume it once, sends of one draft must send one code, and sends of one number from many drafts or of many numbers must stop at the per-number and global limits (the send lock serializes their counts). One submit is held right after it claimed its draft until `sys.dm_exec_requests` reports the second submit blocked by it; both then answer with the one registration. `RegistrationDraftMigrationSqlServerTests` check the migration's tables, indexes, foreign key actions and check constraints, and that its `Down` refuses with 50192 while verification evidence exists and reverts and applies again once it is cleared. The SQLite tests of the same feature are `SignupDraftApiTests` and `SignupSmsModeTests` over HTTP (`SignupWebHost` with the fake sender and a test clock), `RegistrationDraftCleanupTests` and `RegistrationPhoneRulesTests`.

`SerializableTransactionSqlServerTests` (WAS-206) give each test its own connection pool, so the next read gets the transaction's own physical session back, and they assert that through `sys.dm_exec_connections.connection_id` instead of assuming it. Before the next read, a test confirms that the transaction's session is idle in its pool; a session the client discarded, and a next read that got another session, both fail as unchecked. The isolation level is read from `sys.dm_exec_sessions`, and the locks from `sys.dm_tran_locks`. See [../architecture/tenancy.md](../architecture/tenancy.md#serializable-transactions-and-pooled-sessions-was-206).

## Tenant session test hosts

`tests/Wasla.UnitTests/Auth/TenantSessionWebHost.cs` serves the real tenant pipeline in-process (tenant resolution from the Host header, the tenant cookie scheme with its session check, policies, controllers and views) over SQLite databases with fake users; `TenantSessionApiHost` serves Wasla.Api next to it. The SQLite schema comes from `EnsureCreated` with the migration ids recorded, so these tests prove behavior, not SQL Server migrations; the [SQL Server tests](#sql-server-concurrency-tests) cover those.

- **Databases and key ring.** A host started alone creates its databases and deletes them when disposed. `TenantSessionStorage` owns a CentralDb, the tenant database files and a Data Protection key folder that outlive any host. Several hosts started over one storage, each with its own `WebApplication`, service provider and `RecordingTenantDbFactory`, stand in for several Web instances (`TenantSessionInstanceTests`). Disposing a host and building a new one over the same storage is a host recreation inside the test process, not an operating-system process restart.
- **Cookies.** Prefer signing in through the rendered login form (`TenantSessionClient.LoginAsync`, with or without remember-me). `ProtectTenantCookie` protects exactly the claims it is given, optionally as a remember-me ticket, and writes nothing; a hand-built cookie is valid only when its claims name a session stored on purpose with `SeedSession`. Do not make cookie protection register a session: that would hide unknown-session and missing-row failures. `UnprotectTenantCookie` reads a cookie back for assertions.
- **Registration drafts.** The host registers the registration draft services with the fake SMS sender (WAS-192), as `SignupWebHost` does. A browser test that verifies an owner phone reads the code from `host.Services.GetRequiredService<FakeSmsOutbox>()` (`LatestCodeTo`, `MessagesTo`) and can make deliveries fail with `FailDeliveriesWith`; the Development fake outbox endpoint answers 404 on these Production hosts.
- **No secrets in output.** Keep cookie values in memory and assert on them with boolean checks and fixed messages; `Assert.Equal`, `Assert.Null` or a collection assertion on a cookie or `Set-Cookie` header prints it when it fails.
- **Storage failures.** A test fails chosen tenant commands with an EF command interceptor on the tenant database: before they reach the database (a failed revocation or session check), or after the database executed them (a revocation stored but reported as failed, WAS-186). It can also make the tenant database impossible to open. The logout failure tests in `TenantLogoutRevocationTests` cover all three and follow the failure page's own "Try again" to the logout page and its form. They also run each failure with a cookie due for sliding renewal, with and without remember-me, and check that the failure page sends no tenant `Set-Cookie`: the antiforgery token comes from a page of the fresh session, and the cookie is aged afterwards, so the logout is the first request that finds renewal due.
- **Interleavings and time.** The renewal/logout race holds one request after its session check with a validator decorator released by the test, never with a sleep. `RealtimeLogoutTests` runs the live connection check on `ManualTimers`, so each check runs when the test fires it. Expiry and sliding renewal use deliberately aged tickets (the same claims, protected with an earlier issue time), never a wait.

## Repository-root discovery

Many source-contract tests walk parent directories from the test assembly output until they find `Wasla.sln`, then read files under `src/`.

An output directory that is still inside this repository (including a gitignored `artifacts/` folder under the repo) can still find the solution. An output directory outside the repository cannot. Those tests then fail even though the product code is unchanged.

Do not set a global output path outside the repo to “make tests pass.”

## Process-wide console

`Console.Out` and `Console.Error` are shared by every test in the process, and xUnit runs test classes in parallel. A test class that redirects them to capture CLI output, or that runs a CLI command writing to the console, belongs to `CliConsoleCollection` (`tests/Wasla.UnitTests/Cli/CliConsoleCollection.cs`), which runs alone (WAS-171). Otherwise one capture can restore another's already disposed writer, so a later console write fails with `ObjectDisposedException`, or a capture can collect another test's output. Tests that start the CLI as a separate process read that process's own output and need no collection.

## Shared working tree

Other agents may have processes and uncommitted files in this tree.

- Do not `git clean`, reset, or delete another agent’s build output.
- A running `Wasla.Web` (or another project) can lock DLLs under `bin/` and `obj/` and make `dotnet build` fail on copy. Do not stop a process until you have confirmed it belongs to this task.
- If the lock is someone else’s Web process, build or test with an output directory that stays **inside** the repository, or limit the build to projects that are not locked.
- Failures in files you did not change may be concurrent work. Report them separately. Do not revert them to get a green run.

## How to report

Say which of these you actually ran:

- Focused tests
- Full `Wasla.UnitTests`
- `Wasla.PrintBridge.Tests`
- Node tests (all tracked files, or name the files you ran)
- The retired-terminology guard (with the repository variable's current value)
- Browser smoke
- `dotnet build`

Also report warnings, failures, and failures that come from unrelated dirty files. “All tests passed” is only accurate when the full projects you name were run and passed. A focused filter is not the full suite. A green CI run covers the suites listed under [Continuous integration](#continuous-integration) and nothing else; name its scope. A green fast run (a pull request into `dev`) does not include the `Category=Browser` and `Category=WebView2Runtime` tests.
